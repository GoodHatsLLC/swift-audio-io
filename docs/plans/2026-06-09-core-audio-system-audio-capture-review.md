# Core Audio system-audio capture plan — design review

Date: 2026-06-09
Reviewed plan: [`2026-06-09-core-audio-system-audio-capture.md`](./2026-06-09-core-audio-system-audio-capture.md)
Status: complete — the plan was revised to address every confirmed finding below.

## Method

Multi-agent adversarial review. Six dimension-specific finders (correctness, architecture, audio realtime-safety, public-API usability, error/retry model, Core Audio SDK fidelity) critiqued the plan against the real `swift-audio-io` runtime, the host app's reference `AppLocalSystemAudioRecorder`, and the macOS 26.5 SDK headers. Every material finding was then handed to an independent verifier instructed to **refute** it against the cited code/SDK; only findings that survived refutation are reported as confirmed. A completeness critic then swept for gaps the six lenses missed.

## Outcome

- **47** findings raised
- **43** survived adversarial verification (reported below)
- **4** refuted / dropped
- **13** completeness gaps surfaced (folded into the confirmed set)

All confirmed findings have been mitigated in the revised plan — see the plan's revision note and "Resolved decisions".

> Citation note: source-file line references (e.g. `RecordingEngineRuntime.swift:486`) are stable; plan line references (e.g. "line 254") point at the **as-reviewed** plan, before the revision that addressed them, so they will not match current line numbers in the revised plan.

### Synthesized review

### 1. Verdict

The plan is **fundamentally sound**. The architectural thesis — unify system audio behind `AIOEngine.startRecording`, reuse the existing converter/ring-buffer/writer/receiver pipeline via `processAudio`, and isolate the Core Audio machinery behind a `RecordingCaptureBackend` boundary — is the right shape, and the source-specific enum config, the public-not-SPI decision, and the conservative retry policy are all defensible. The single biggest risk is that **every load-bearing integration seam between the new backend and the existing runtime is described aspirationally but left unspecified** — specifically the four seams where the new code must mesh with battle-tested mic code: (a) the IOProc-to-`processAudio` realtime handoff, (b) the tap-source-ASBD-to-converter wiring, (c) active-backend dispatch through `hardStop`/`gracefulStop`/`cleanUp`, and (d) the `OSStatus`→`RecordingError.isTransient` retry gate. Three of these are "draw the box but not the wires" gaps that will surface as compile failures or silent dropouts in Phase 2–4 rather than design dead-ends. They are cheap to close on paper now and expensive to discover mid-implementation. Close them before writing code.

### 2. Findings by severity

#### CRITICAL

**C1. No active-backend state field; lifecycle teardown is hardcoded to AVAudioEngine.**
`hardStop()` (RecordingEngineRuntime.swift:486–509) and `gracefulStop()` (512–554) unconditionally call `engine.inputNode.removeTap`, `engine.stop()`, `engine.reset()`, and `cleanUp()` (557–580) resets only recorder state with zero backend awareness. `RecordingState` (RecordingSupportTypes.swift:241–253) has no `activeBackend`/`sourceKind` discriminant, so the active source is invisible to callers of `stopRecording`/`rotateRecordingFile` and to route-change handling. The plan says "track the active source backend" (line 254) but never names the field, its type, or the dispatch points. For system audio these methods must instead destroy the IOProc, aggregate device, and tap — calling `removeTap` on a non-existent inputNode is undefined, and skipping Core Audio teardown leaks HAL objects on every stop/failure. A stop-mic-then-start-system-audio sequence will tear down the wrong backend.

*Change:* Add `package var activeBackend: RecordingCaptureBackend?` (or an enum discriminant `.microphone | .systemAudio`) to `RecordingState`. Set it in `startRecording` after `warm()` succeeds. Make `hardStop`/`gracefulStop`/`cleanUp` dispatch: if `.microphone`, run the existing engine teardown; if `.systemAudio`, call `backend.stop()`/`backend.cleanup()`; if nil, no-op. Also dispatch the `warm()` failure path on whichever backend was partially initialized. Specify this in Phase 4 as a prerequisite — and per the byte-equivalence requirement (line 450), the mic backend's tap-removal/engine-stop must itself become a backend method, not stay implicit in `hardStop`. Add a test: start mic → stop → start system audio, assert `engine.inputNode.removeTap` is never called during system-audio teardown.

> Note: this was independently flagged by five review dimensions. One verifier argued HIGH (it's a planning gap, not a shipping bug); I keep it CRITICAL because it blocks coexistence of the two backends in one codebase and the leak is silent.

#### HIGH

**H1. `OSStatus`→retry classifier is not wired to the `isTransient` gate.**
The reconciliation loop retries *only* when `error.isTransient == true` (RecordingRuntime.swift:100), and `RecordingError.isTransient` returns true *only* for `.session(sessionError)` where `sessionError.isTransient` holds (RecordingError.swift:97–103; SessionError.swift:54–59 → only `.notReady`). The plan proposes new top-level cases `captureSourceUnavailable`/`captureSourceFailed` (lines 167–169) and a detailed 11-row retry table (204–217) plus a "test-only classifier" (228–229), but never connects them: as written, top-level cases default `isTransient` to `false`, so `kAudioHardwareNotReadyError` will be *correctly classified as retryable by the table and never retried by the loop.* The "test-only classifier" is also suspect — the gate is in production code, not tests.

*Change:* Commit to one path in Phase 1 before any system-audio startup is written:
- **(A)** Wrap retryable HAL errors in `.session(.notReady(details:))` (add a `SessionError` case like `.captureSourceNotReady` if `.notReady` is semantically wrong) so the existing gate applies unchanged; or
- **(B)** Make the new cases store the `OSStatus` and compute `isTransient` via a package-internal `func isOSStatusTransient(_:) -> Bool`, extending `RecordingError.isTransient` to cover them.

Make the classifier production code, not test-only. Add a unit test covering all 11 table rows (204–217), asserting the resulting `RecordingError.isTransient` matches the table's retry decision (e.g., `kAudioHardwareNotReadyError` → true; `kAudioDevicePermissionsError` → false).

> Flagged by six dimensions. Recommended mapping: `kAudioHardwareNotReadyError` and "aggregate device created but no usable device" → transient; everything else terminal.

**H2. Converter input format / tap-source ASBD acquisition and validation is unspecified.**
`processAudio` guards `formatsCompatible(converterInputFormat, buffer.format)` and *silently* bails with `recordTapError(.converterMissing)` on mismatch (RecordingEngineRuntime.swift:628–636). For mic, `converterInputFormat` comes from the post-install `AVAudioEngine.inputNode` format (AIOEngine+TapSetup.swift:136–140). System audio has no inputNode — the source ASBD must come from `kAudioTapPropertyFormat` (the host app constructs `AVAudioFormat` from `tap.format` ASBD, AppLocalSystemAudioRecorder.swift:158). The plan says "rebuild an `AVAudioPCMBuffer` with the tap source format" (283) but never specifies *when/how* the ASBD is read, whether it is validated against the requested `InputConfiguration`, or what happens on an unsupported (compressed/exotic) format. If a mismatch is only discovered in the first IOProc callback, the converter is already built wrong and frames drop silently.

*Change:* Specify in the backend-design/start sections (not deferred to a spike): immediately after `AudioHardwareCreateProcessTap` succeeds, read `kAudioTapPropertyFormat`, build an `AVAudioFormat` from the ASBD, and **validate before starting the IOProc** — sample rate matches or converts to `InputConfiguration.sampleRate`, channel count matches `InputConfiguration.channels`, format is linear PCM (reject compressed/exotic). On mismatch, destroy the tap and throw `RecordingError.invalidConfiguration` *before* `recordingStarted` is emitted. Then call `makeTapConversionArtifacts(inputFormat: <validated tap format>, …)` and populate `state.tapConverter`/`tapConverterInputFormat`/`tapConverterOutputFormat`/`tapConvertedBuffer` via `applyTapInstallResult` or an equivalent, before the first buffer. State explicitly that post-start tap-format changes are unsupported and stop the recording with an error. Add a fake-backend test asserting a format mismatch surfaces an error pre-`recordingStarted`, not a silent drop.

> Flagged by five dimensions (one as `critical`, two as `medium`→corrected to HIGH). HIGH is correct: the reuse strategy is sound; the gap is the missing pre-IOProc validation contract.

**H3. Converter-artifact ownership across the backend boundary is undefined.**
Converter artifacts (`tapConverter`, `tapConverterInputFormat`, `tapConverterOutputFormat`, `tapConvertedBuffer`) live in `RecordingState` (RecordingSupportTypes.swift:249–252), are read by `processAudio` through a cached `TapSnapshot` under `tapSnapshotLock` (RecordingEngineRuntime.swift:603–620), and are updated atomically by `applyTapInstallResult` (AIOEngine+TapSetup.swift:176–195). The proposed `RecordingCaptureBackend` (lines 236–241) returns only `sourceFormat` + `start`/`stop`/`cleanup` — it says nothing about who builds, owns, or releases the converter for system audio. This risks a stale converter in `processAudio` after a backend swap, or double-free if both common code and the backend try to release.

*Change:* Decide ownership explicitly. Recommended: **common code owns all converter artifacts.** Backends vend only `sourceFormat`; common code builds the converter (`sourceFormat → processingFormat`), pre-allocates `convertedBuffer`, and updates the `TapSnapshot` under `tapSnapshotLock`. `cleanUp()` clears artifacts only when common-owned. Add a test that `processAudio` never observes a stale converter after a backend swap. (If instead the backend owns them, document the lock-synchronization contract for snapshot updates.)

**H4. The Core Audio wrapper types are net-new work mis-framed as a "move."**
The plan says "Move the generic machinery from the host app" (lines 258–266), but `AudioHardwareSystem.shared`, `AudioHardwareTap`, `AudioHardwareAggregateDevice`, and their methods (`makeProcessTap`, `makeAggregateDevice`, `destroyProcessTap`, `process(for:)`) used by the host app (AppLocalSystemAudioRecorder.swift:150–177) are **neither Apple SDK symbols nor present in this repo** — they are host-app-local wrappers. Phase 3 will discover these must all be authored fresh, with ownership and visibility decisions, on top of the lifecycle refactor that currently has zero backend abstraction. The plan's scoping understates this.

*Change:* In Phase 0, enumerate each missing wrapper, its required API surface, and its source location in the host app. Add an explicit Phase 0/Phase 3 task: "Design and write `AudioHardwareSystem`/`AudioHardwareTap`/`AudioHardwareAggregateDevice` and package-internal `CoreAudioProcessTapSession`." For each, decide visibility (almost certainly package-internal in `AIORecording`, not public) and lifecycle ownership (e.g., `CoreAudioProcessTapSession` owns tap+device+IOProc).

**H5. IOProc realtime handoff is unspecified and the reference implementation is RT-unsafe.**
The plan says "copy or enqueue only" / "bounded handoff structure or serial queue item" (270, 281–282) but never names the data structure. The host app's actual path heap-allocates `Data(bytes:count:)` per channel and calls `sampleQueue.async` *inside the IOProc* (AppLocalSystemAudioRecorder.swift:197–207) — both forbidden on a realtime thread (malloc can block on the heap lock; `DispatchQueue.async` can block on a contended queue). The mic path, by contrast, does only atomic increments + lock-free `SPSCRingBuffer.write()` from the callback (RecordingEngineRuntime.swift:272–283), with no allocation (583–637). "Serial queue item" as written does not rule out re-creating the host app's unsafe pattern.

*Change:* Mandate in the design: "The IOProc must enqueue into a pre-allocated, lock-free handoff structure (SPSC ring buffer or object pool) and must not call `malloc`, `DispatchQueue.async`, or any blocking API." Define the struct layout (frame count, buffer pointers, timing fields) and its capacity/overflow semantics (drop-on-full vs. bounded). Add to Phase 0 a throwaway harness that starts/stops a real process tap and measures IOProc latency / confirms no page faults or allocations under load. Add a test recording 10s and asserting no heap allocation from the IOProc thread.

**H6. IOProc timing fields (`mHostTime`/`mSampleTime`) capture is unspecified — and the reference impl drops them.**
The plan promises `recordingTimingSnapshot()` stays meaningful "whenever the HAL provides host time" (291–292), but the host app's `SystemAudioSampleChunk` captures only `frameCount` + buffers and discards `inInputTime` entirely; its writer synthesizes a sample time with no host time. The mic path reads `hostTime`/`sourceSampleTime` from `AVAudioTime` and anchors first-capture timing (RecordingEngineRuntime.swift:711–729); `TimingPacket` carries `hostTime`/`sourceSampleTime`/`sourceSampleRate` (RecordingSupportTypes.swift:219–239). The plan never states that the handoff must extract and preserve the `AudioTimeStamp` fields.

*Change:* Specify: the IOProc extracts `mHostTime` (if `mFlags & kAudioTimeStampHostTimeValid`) and `mSampleTime` (if `kAudioTimeStampSampleTimeValid`) from `inInputTime`, stores them in the handoff struct, and threads them into `TimingPacket`. Confirm `TimingPacket` is the intended internal timing variant (it already has the right fields) rather than inventing a new one. Adapt `processAudio` to accept direct timing values (not just `AVAudioTime`), and anchor `recordingFirstHostTimeAtomic`/`recordingFirstSourceSampleTimeAtomic` from the first valid host time for both backends. Note that system-audio `sourceSampleTime` may not be monotonic. In Phase 0, log raw `inInputTime` from a real recording to confirm field availability and domain (`mHostTime` should be `mach_absolute_time`). Add a fake-backend test injecting a known `AudioTimeStamp` and asserting `recordingTimingSnapshot()` returns the correct non-zero host time.

**H7. IOProc buffer size and `convertedBuffer` capacity are not tied to the HAL buffer size.**
For mic, `convertedBuffer` capacity is pre-sized from `tapBufferSize * tapFrameRatio` (AIOEngine+TapSetup.swift:24–27); `processAudio` records `.bufferTooSmall` on overflow (RecordingEngineRuntime.swift:647–651). System audio has no `tapInterval` — `AudioDeviceCreateIOProcIDWithBlock` delivers HAL-determined, possibly variable buffer sizes the caller does not control. If the IOProc delivers more frames than pre-allocated, frames drop silently. The plan never addresses discovering or respecting the aggregate device's buffer size.

*Change:* Add to Phase 0: after creating the aggregate device and before starting IO, query `kAudioDevicePropertyBufferFrameSize` and `kAudioDevicePropertyUsesVariableBufferFrameSizes`; pre-allocate the handoff and converter input buffer to that max. Pass the discovered size into `makeTapConversionArtifacts` (or a system-audio variant). If the property is unqueryable or reports zero, fail startup with a diagnostic error. Document the lifecycle difference vs. mic: system audio cannot survive a tap resize the way the mic path can (`requestTapResize` is mic-only), so an oversized buffer is a terminal `.bufferTooSmall` stop.

**H8. `updateRecordingTapInterval` will not compile after the config refactor.**
`updateRecordingTapInterval` reconstructs the config via `RecordingConfiguration(inputConfiguration:, outputConfiguration:, tapInterval:, outputDestination:)` (RecordingRuntime.swift:208–213, reading a top-level `tapInterval`). The new shape (lines 69–73) has `input: RecordingInput` and no top-level `tapInterval` — that constructor no longer exists, so Phase 2's "existing microphone tests pass" gate (line 451) fails at compile time.

*Change:* Specify the post-refactor path: either (1) a factory `RecordingConfiguration.withUpdatedTapInterval(_:)` that pattern-matches the `.microphone` case and reconstructs with the new interval nested in `MicrophoneRecordingInput` (and decide its behavior for `.systemAudio` — throw or no-op), or (2) mutate the `MicrophoneRecordingInput` in the in-flight recording state directly without rebuilding the full config.

**H9. `SystemAudioProcessObjectID` has no discovery/conversion API.**
`SystemAudioProcessObjectID` is a raw `UInt32` wrapper (lines 107–109) with no way to obtain an ID from a PID or bundle ID. The host app uses `AudioHardwareSystem.shared.process(for: getpid())` (AppLocalSystemAudioRecorder.swift:308) — a private wrapper not in the public surface. Without a discovery API, callers cannot self-exclude or target a process. This also leaves ambiguous *who* implements the "default system audio excludes the current process" test (line 152) — the host app or AudioIO.

*Change:* Pick one and state it: (1) provide public `SystemAudioProcessObjectID(processID:)` / `.currentProcess` (requires porting the `AudioHardwareSystem` wrapper as public surface), or (2) make `processObjectIDs` optional and default to excluding the current process by bundle identifier when available (lowest friction). Clarify which layer owns process lookup for the self-exclusion test.

> Overlaps with H10's process-lookup-failure path; resolve them together.

**H10. Process-lookup-failure fallback is under-defined.**
The retry table row "Process lookup for current process fails → No; fall back to bundle identifier exclusion when available" (line 215) doesn't say how the bundle ID is obtained, what "record the degraded exclusion behavior" means, or whether the fallback is automatic.

*Change:* Specify: at start, attempt object-ID exclusion of the current process; on failure, if `Bundle.main.bundleIdentifier` exists, augment filters with it and set `restoresProcessesByBundleIdentifier = true`; emit a debug log or a new `AudioIOEvent` (e.g., `.processTapDegradedExclusion`); do **not** fail recording. Document in `SystemAudioRecordingInput` that self-exclusion is by object ID *or* bundle ID, implementation-determined. Add a test that lookup failure triggers the bundle-ID fallback without halting startup.

#### MEDIUM

**M1. Partial-start cleanup is not wired into the reconciliation retry loop, and its order/error-tolerance is unspecified.**
The plan asserts "every created tap/device must be destroyed before retry" (207) and cleanup must survive partial failure (275–276), but the reconciliation loop (RecordingRuntime.swift:85–116) catches and retries with no visible cleanup step; the mic precedent is `warm()` → `hardStop()` (RecordingEngineRuntime.swift:388–393). The host app's `cleanup()` can itself fail and swallows the error (AppLocalSystemAudioRecorder.swift:47–50).

*Change:* Specify that `RecordingCaptureBackend.cleanup()` is best-effort and non-throwing, and that any `backend.start()`/post-start failure calls `backend.cleanup()` before the error propagates to reconciliation (matching `warm()`→`hardStop()`). Document the teardown order: (1) stop IOProc (tolerate `kAudioHardwareNotRunningError`), (2) destroy IOProc, (3) destroy aggregate device, (4) destroy process tap — capturing the first non-zero `OSStatus` but continuing, logging failures without blocking the next retry.

**M2. IOProc handoff queue's RT-safety is asserted but not analyzed.** Subsumed by H5 — the implementation rules (268–276) imply safety but the structure isn't named. Resolve with H5; no separate action.

**M3. `PublicAPISnapshot.swift` / `Exports.swift` additions are not enumerated.**
`PublicAPISnapshot.swift:49` pins only `RecordingConfiguration`; `Exports.swift:80–81` re-exports `RecordingConfiguration`/`RecordingError`. The plan says "add all new public symbols" (129–130, 442) without the concrete list or `#if os(macOS)` gating, risking an incomplete stability net.

*Change:* In Phase 1, add `public typealias` exports for `RecordingInput`, `MicrophoneRecordingInput`, and `#if os(macOS)`-gated `SystemAudioRecordingInput`, `SystemAudioProcessSelection`(+`.Mode`), `SystemAudioProcessObjectID`. Add matching `_ = T.self` snapshot lines under the same gates, and verify the snapshot compiles on both iOS (macOS symbols excluded) and macOS.

**M4. Mic config-refactor call-site audit is missing.**
Beyond H8, ~10 sites read `configuration.inputConfiguration` / `tapInterval` / `processingFormat` / `tapConfiguration()` directly (e.g., RecordingConfiguration.swift:55,423; RecordingEngineRuntime.swift:196–207). The plan promises byte-equivalent mic behavior (450) but provides no call-site audit or migration-helper strategy; a mis-cast enum case breaks the mic path silently.

*Change:* Before Phase 2, audit all such references and decide for each whether it reads from the enum-specific input or a new computed property on `RecordingConfiguration` that safely extracts the field. Clarify whether `processingFormat`/`tapConfiguration()` stay computed (and how they behave for `.systemAudio`, since they currently derive from `inputConfiguration`). Prefer compiler-enforced accessors (guard-case helpers). Land the config refactor as a standalone PR ahead of system-audio code, gated on the full mic test suite.

**M5. No channel-count validation for system audio (mono/stereo only).**
The plan says "mono and stereo initially" (118–119) but adds no validation; `validateRecordingChannelCapacity` (RecordingEngineRuntime.swift:410–446) checks a maximum, not a system-audio 1–2 gate. The host app's `makeTapDescription` implicitly assumes ≤2 channels (AppLocalSystemAudioRecorder.swift:291). A 5.1 config would silently downmix or fail late.

*Change:* In `warm()` (before backend start), throw a clear error (e.g., `RecordingError.invalidConfiguration` or `.unsupportedChannelCount(requested:maximum:2)`) when `.systemAudio` requests >2 channels. Add a test: 6-channel system audio throws at `warm()`.

**M6. `aggregateDeviceUIDPrefix` is public with no documented semantics.**
Exposed as a public field (line 92); the host app hard-codes `com.example.system-audio.{UUID}` (AppLocalSystemAudioRecorder.swift:314–327). No format/uniqueness/collision guidance — bad prefixes yield cryptic Core Audio "device creation failed."

*Change:* Either hard-code the UID scheme (`com.audioio.system-audio.{UUID}`) and drop the field, or document the format (reverse-domain), uniqueness guarantees (UUID suffix), and use case if customization is genuinely needed.

**M7. Public/`@_spi` split for the reconciliation start path is unaddressed.**
`AIORecording` is `@_spi(Advanced)` because the reconciliation start API is SPI (Exports.swift:32–38), yet `.systemAudio` is public (59). Third-party callers see public `.systemAudio` but the retry-capable start path is SPI — a split that matters more for system audio (Core Audio startup is brittle) than for mic.

*Change:* Either promote `startRecordingWithReconciliation`/`setDesiredRecordingState` to public once Phase 0 validates system-audio stability, or document on `RecordingInput.systemAudio` that graceful retry requires the `@_spi(Advanced)` path and why.

**M8. Unknown-`OSStatus` handling has no catch-all / surfacing.**
The table defaults unknown statuses to no-retry (214) but doesn't say whether they're logged or surfaced; existing `RecordingError` cases all carry specific descriptions.

*Change:* Add a catch-all `case coreAudioFailure(osStatus:operation:details:)`, log unmapped statuses with operation context, and always surface them via `AudioIOEvent.error` so failures aren't hidden.

### 3. What the plan gets right (don't touch)

- **The core architecture.** Unifying behind `AIOEngine.startRecording`, reusing `processAudio` → ring buffers → writer/receiver loops, and isolating Core Audio behind `RecordingCaptureBackend` is correct and avoids the host app's duplicated writer/receiver path. The seams need wiring (Section 2), but the boxes are in the right places.
- **Source-specific enum config.** Making `RecordingInput` an enum so `tapInterval` is mic-only and process selection is system-audio-only is the right call over a generic `tapInterval` that half-applies. Accept the breaking change.
- **`.systemAudio` public, not SPI** (59–61) — correct for a pre-1.0 engine-level capability.
- **Conservative retry policy.** Retry only bounded not-ready startup failures; treat permission/stale-object/unsupported/format/filesystem/unknown as terminal; no auto-restart of a running recording post-failure until validated (179–227). The classifications in the table are sound — only the *wiring* to `isTransient` is missing (H1).
- **RT discipline as stated.** "Copy/enqueue only, no file I/O, no Swift concurrency, no receiver calls on the IOProc" (268–276) is the right doctrine — it just needs a concrete lock-free structure (H5).
- **Error model direction.** Extending `RecordingError` with a source *description string* rather than embedding the config enum (161–175) is good ABI/equality hygiene.
- **Test plan and phasing breadth.** The fake-backend test matrix (353–362), per-row retry tests, iOS-unavailability test, and the "mic tests pass before adding system audio" gate are exactly right.

## Appendix A — confirmed findings (traceability)

Each entry is a finding that survived adversarial verification, with the evidence it cites and the verifier's verdict. Severity is the verifier-corrected severity where it differs from the finder's original.

### CRITICAL

#### `backend-state-lifecycle-dispatch` — No explicit active-backend state tracking; hardStop/gracefulStop/cleanup may dispatch on wrong source

- **Dimension:** architecture
- **Severity:** critical _(finder said high)_
- **Plan location:** RecordingState or RecordingRuntimeState will need to track the active source backend so stopRecording, hardStop, gracefulStop, route-change handling, and cleanup can stop the right capture source.
- **Problem:** The plan acknowledges the need but does not specify WHERE the backend reference lives or HOW it's accessed. Currently (RecordingEngineRuntime, lines 486-552), hardStop() unconditionally calls engine.inputNode.removeTap and engine.stop, then cleanUp(). For system audio, there is no inputNode—the IOProc is a separate HAL entity. The code must dispatch: hardStop → if backend==.mic then engine.stop() else if backend==.systemAudio then ioProcSession.stop(). However, hardStop() is NOT wrapped in active-backend gating. If recording is stopped and restarted with a different source before cleanUp completes, or if route change fires during cleanup, the wrong backend may be torn down. Additionally, RecordingState (line 241-253) has no backend field, so the active source is invisible to callers of stopRecording/rotateRecordingFile.
- **Evidence:** Sources/AIORecording/RecordingEngineRuntime.swift:486-509 (hardStop unconditionally manipulates engine, removes tap on installedTapBus, calls cleanUp); RecordingEngineRuntime.swift:512-554 (gracefulStop also unconditionally engages engine control queue and tap removal); RecordingEngineRuntime.swift:557-580 (cleanUp resets state.recordingConfiguration and state.recordingWriter but has no backend awareness); Sources/AIORecordingSupport/RecordingSupportTypes.swift:241-253 (RecordingState has no activeBackend or sourceKind field)
- **Recommendation:** Add `package var activeBackend: RecordingSourceBackend?` (enum: .microphone, .systemAudio) to RecordingState. Update hardStop() and gracefulStop() to dispatch on activeBackend before manipulating engine or invoking backend.cleanup(). Update cleanUp() to call backend.cleanup() if activeBackend is set. Update startRecording to store activeBackend after warm() succeeds. Add a test: start mic → stop → start system audio → verify mic engine is not touched. Also add a route-change handler test showing the correct backend receives notifications.

## Appendix C — completeness gaps

Raised by the completeness critic after the six lenses ran. These overwhelmingly reconverged on the same load-bearing seams (active-backend dispatch, ASBD→converter wiring, OSStatus→`isTransient`, the realtime handoff/timing), which is corroborating signal rather than new scope; all are covered by the confirmed findings above and the plan revision.

- **[high]** config-refactor-incompleteness
  The plan removes top-level `tapInterval` from RecordingConfiguration and moves it into MicrophoneRecordingInput. However, updateRecordingTapInterval (RecordingRuntime.swift:193-229) reconstructs RecordingConfiguration by reading all fields including the old `tapInterval` field. The refactored RecordingConfiguration enum model cannot be reconstructed the same way without explicit specification of the migration.
  _Evidence:_ RecordingRuntime.swift:208-213 shows updateRecordingTapInterval reads current config and reconstructs with: `RecordingConfiguration(inputConfiguration:, outputConfiguration:, tapInterval:, outputDestination:)`. Plan section 'Public API shape' (lines 69-73) specifies new shape has `input: RecordingInput` enum, not `inputConfiguration` and separate `tapInterval`. This constructor call will not compile post-refactor.
- **[high]** error-transition-unspecified
  The plan proposes new OSStatus-to-retry classifier but does not specify how this feeds the existing `RecordingError.isTransient` property. The reconciliation loop only retries when `error.isTransient == true`. New system-audio-specific errors are not yet defined, and it is unclear how the classifier produces errors where isTransient reflects retry decisions.
  _Evidence:_ RecordingRuntime.swift:100 gates retry on `error.isTransient`; RecordingError.swift:98-103 shows isTransient only returns true for `.session(sessionError)` where sessionError.isTransient is true. Plan section 'Reconciliation retry investigation' (lines 202-217) proposes OSStatus→retry table but 'Error model' section (lines 161-176) does not link them to RecordingError.isTransient or specify how new cases integrate.
- **[high]** converter-reuse-format-mismatch
  The processAudio callback validates format compatibility but does not specify how the tap source ASBD is obtained and used to build the converter for system audio. For microphone, converterInputFormat comes from AVAudioEngine inputNode post-tap install. System audio has no AVAudioEngine input node; the tap source ASBD must be extracted from HAL and the converter built from that, with pre-allocation of convertedBuffer sized to the IOProc buffer size.
  _Evidence:_ AIOEngine+TapSetup.swift:136-140 shows makeTapConversionArtifacts requires inputFormat pre-computed. RecordingEngineRuntime.swift:631-632 validates formatsCompatible(converterInputFormat, buffer.format) and bails with .converterMissing if false. Plan does not specify which HAL property reads the ASBD or how IOProc buffer size is discovered and pre-allocated.
- **[high]** timing-handoff-incomplete
  The plan states timing should be passed from IOProc to the pipeline but does not specify the 'bounded handoff structure or serial queue item' that carries mHostTime and mSampleTime. The IOProc receives AudioTimeStamp with timing fields directly, but the handoff mechanism and integration into TimingPacket is not detailed.
  _Evidence:_ RecordingEngineRuntime.swift:712-729 shows processAudio reads hostTime and sourceSampleTime from AVAudioTime. TimingPacket (RecordingSupportTypes.swift:219-239) has hostTime and sourceSampleTime fields. Plan mentions 'IOProc copies the buffer payload into a bounded handoff structure' (line 282) but does not name the type or specify how mHostTime/mSampleTime flow through it.
- **[high]** backend-dispatch-incomplete
  The plan proposes tracking the active backend but hardStop() (RecordingEngineRuntime.swift:486-509) and gracefulStop() (512-554) unconditionally manipulate AVAudioEngine without backend-aware dispatch. For system audio, these calls must be skipped and instead IOProc and aggregate device destroyed. The plan does not show where or how dispatch happens.
  _Evidence:_ hardStop() line 493-502 only knows AVAudioEngine: removeTap, stop, reset. gracefulStop() line 520-524 also only knows AVAudioEngine. Plan line 233-254 proposes RecordingCaptureBackend protocol but does not show integration into these methods, nor specifies which state field holds the active backend reference.
- **[medium]** reconciliation-cleanup-gap
  The plan explicitly warns that 'every created tap/device must be destroyed before retry' (line 207) but does not specify when/where Core Audio cleanup happens in the reconciliation loop. If warm() partially creates a tap, then fails to create the aggregate device, the cleanup must happen before reconcileRecordingState retries.
  _Evidence:_ RecordingRuntime.swift:85-116 reconcileRecordingState loop catches error and retries without explicit cleanup between attempts. RecordingEngineRuntime.swift:388-393 shows warm() has a catch block that calls hardStop() on failure, but for system-audio, if Core Audio tap creation fails partway, the cleanup path is not wired into the reconciliation error handler.
- **[medium]** realtime-safety-queue-unspecified
  The plan states the IOProc must 'copy or enqueue only' and proposes a 'bounded handoff structure or serial queue item' but does not specify whether the handoff is pre-allocated, lock-free, or uses a DispatchQueue. The host app's IOProc uses DispatchQueue.async (potentially blocking) and Data heap allocations. The plan forbids these but does not name the actual handoff mechanism.
  _Evidence:_ AppLocalSystemAudioRecorder.swift:197-207 calls Data(bytes:count:) and DispatchQueue.async, both violating RT safety. RecordingEngineRuntime.swift:272-283 (mic path) uses atomic increments and SPSCRingBuffer writes with no queue dispatch from callback. Plan line 268-276 forbids unsafe handoffs but line 281-282 only says 'bounded handoff structure or serial queue item' without explicit design.
- **[medium]** public-api-snapshot-incomplete
  The PublicAPISnapshot test currently pins RecordingConfiguration only. After the refactor, RecordingInput, MicrophoneRecordingInput, SystemAudioRecordingInput, SystemAudioProcessSelection, and SystemAudioProcessObjectID are new public types that must be pinned in the snapshot.
  _Evidence:_ PublicAPISnapshot.swift line 49 shows `_ = RecordingConfiguration.self` but no entries for new types. Plan section 'Phase 1' (line 442) says 'Update `AudioIO` exports and public API snapshot tests' but does not show the additions or clarify #if os(macOS) gating for system-audio-only types.
- **[high]** backend-protocol-converter-coupling
  The proposed backend protocol returns only sourceFormat and start/stop/cleanup. However, converter artifacts (converter, converterInputFormat, converterOutputFormat, convertedBuffer) are stored in RecordingState and the processAudio callback reads them via cached TapSnapshot. System audio will also need to build a converter, but the plan does not specify where converter artifacts live, who owns them during failures, or how the cached snapshot updates.
  _Evidence:_ RecordingSupportTypes.swift:249-252 shows RecordingState has converter fields; RecordingEngineRuntime.swift:603-620 shows processAudio reads all four from TapSnapshot; AIOEngine+TapSetup.swift:176-195 shows applyTapInstallResult atomically updates all four in a lock. Plan does not show how system audio populates these or who owns them.
- **[critical]** backend-state-lifecycle-dispatch
  No explicit active-backend state tracking in RecordingState. The code must dispatch hardStop/gracefulStop/cleanup based on which backend is active (microphone vs. system-audio). If recording is stopped and restarted with a different source before cleanup completes, the wrong backend may be torn down or objects leak.
  _Evidence:_ RecordingState (RecordingSupportTypes.swift:241-253) has no activeBackend or sourceKind field. hardStop() and gracefulStop() have no backend dispatch. Plan line 254 says 'track the active source backend' but does not specify the field name, type, or which methods dispatch on it.
- **[high]** error-classification-transient-gate
  The plan proposes a detailed OSStatus retry table and test-only classifier, but does NOT specify how it feeds into RecordingError.isTransient. The reconciliation loop (RecordingRuntime.swift:100) checks only `error.isTransient`. For new system-audio-specific errors (captureSourceUnavailable, captureSourceFailed), the plan does not state whether isTransient must be overridden or if the classifier returns a boolean that constructs the right error type.
  _Evidence:_ RecordingError.swift:97-103 shows isTransient only returns true if wrapped SessionError.isTransient is true. Plan line 209 says 'kAudioHardwareNotReadyError → Yes, bounded' but does not name the mapped RecordingError case or show how isTransient gate is satisfied.
- **[high]** audioio-wrapper-layer-missing-scope
  The plan assumes portable AudioHardwareSystem, AudioHardwareTap, AudioHardwareAggregateDevice wrappers but does not specify where these are currently defined or whether they should be ported as-is. These types are not in the swift-audio-io repo and not Apple SDK symbols — they are custom wrappers in the host app that must be understood before porting.
  _Evidence:_ AppLocalSystemAudioRecorder.swift lines 150-177 reference AudioHardwareSystem.shared, makeProcessTap(), makeAggregateDevice(), destroyProcessTap() which are NOT defined in tracked host-app source shown and NOT Apple SDK symbols. Plan line 259 says 'Move the generic machinery' but does not clarify scope, ownership, or porting requirements.
- **[high]** converter-format-validation-system-audio-gap
  System audio converter may silent-fail if formats don't match; no pre-validation of tap source ASBD. If the IOProc thread discovers a format mismatch during the first callback, the converter is already built with wrong assumptions and processAudio drops samples silently.
  _Evidence:_ RecordingEngineRuntime.swift:628-636 guards formatsCompatible() and silently bails with .converterMissing. Plan does not mention pre-start ASBD validation or what happens if the source format is unsupported (compressed audio, exotic sample rate, mismatched channels).
